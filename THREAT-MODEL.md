# THREAT-MODEL.md — HackFlow

Bonus challenge (PLAN.md Phase 4): each attack paired with the mitigation
already built, not new work — a write-up of what the platform already enforces,
cross-checked against the code that enforces it. Entries 1–11 cover Phases 0–4,
12–16 account recovery (Phase 9), 17–24 the multi-event audit (Phase 10), and 29 framing.

| # | Attack | Mitigation already built | Where |
|---|--------|---------------------------|-------|
| 1 | A judge scores another judge's assignment. | `submit_score`/`get_my_score` check `assignment.judge_id != user.id` and refuse with 403 before touching the score row. | `api/app/scoring/router.py` |
| 2 | A participant self-promotes to judge or organizer. | `judge` has no self-service signup path at all — the only route in is a single-use, expiring `JudgeInvite` issued by an organizer/admin. Role changes otherwise only happen server-side. | `api/app/judging/invites.py` |
| 3 | A judge is assigned a submission from their own team (grading themselves). | `build_conflict_set` excludes every (judge, submission) pair where the judge shares a team with that submission, computed from real `TeamMembership` rows before assignment runs — not left to organizer discipline. | `api/app/judging/assignment.py` |
| 4 | An organizer edits rubric weights after scoring starts, invalidating existing scores without anyone noticing. | `upsert_rubric` checks for any `Score` joined through `JudgeAssignment` for the event and refuses the edit with 409 once one exists. | `api/app/judging/router.py` |
| 5 | Results or vote counts leak before the reveal time an organizer promised. | `may_see_results` / `results_are_public` gate every results-bearing endpoint (`/results`, `/public-results`, CSV exports, certificates) server-side against `results_hidden_until` — never just hidden in the UI. Organizers/admins are the one documented exception, since they run the event. | `api/app/events/visibility.py` |
| 6 | A participant votes twice, or a script spams the vote/comment endpoints. | A unique constraint on (submission, voter) blocks duplicate votes at the DB level; a process-global rate limiter throttles comment/vote writes per user. | `api/app/voting/` |
| 7 | Path traversal via a crafted static-file request (`/../../etc/passwd`) reads outside the SPA's static directory. | The SPA catch-all resolves the candidate path and requires `candidate.is_relative_to(STATIC_DIR_RESOLVED)` before serving it. | `api/app/main.py` |
| 8 | A signed judge participation record is edited after issuance (inflating a submissions-scored count) and passed off as genuine. | Records are signed with a server-held Ed25519 key over a canonical (sorted-key) JSON encoding; any byte change fails `verify_record` against the published public key — no server round-trip needed to catch it. | `api/app/crypto.py` |
| 9 | A malicious LIKE-wildcard in a gallery search (`%`, `_`) is used to broaden a search beyond what the query box implies. | Gallery search escapes `%`/`_`/the escape character itself before building the `LIKE` clause. | `api/app/submissions/router.py` |
| 10 | An organizer deletes an event that still has teams/submissions, destroying participant work with one click. | `delete_event` counts dependent teams/submissions first and refuses with a 409 naming the exact count, rather than cascading or hitting a bare FK-violation 500. | `api/app/events/router.py` |
| 11 | A bulk-imported event silently inherits someone else's judge assignments/scores, misattributing who actually judged it. | Import intentionally does not round-trip assignments or scores — only event config, rubric, teams, and submissions. An imported event starts unjudged; assignment and scoring are re-run fresh against real accounts on the new event. | `api/app/scoring/router.py` (`import_event`) |
| 12 | A stolen session cookie keeps working after the victim resets or changes their password. | Cookies carry the account's `session_version`, which every password change or reset increments; `get_current_user` refuses any cookie with an older version, so one change signs out every device. | `api/app/auth/deps.py`, `api/app/auth/session.py` |
| 13 | "Forgot password?" is used to find out which email addresses have accounts. | The response body and status are identical for known and unknown addresses, including when a rate limit is hit, and the email is sent in the background so the response never waits on the mail server. With email off, the page asks for nothing at all. *Residual:* a known address also writes a database row, a sub-millisecond timing difference judged not worth padding. | `api/app/auth/router.py` (`forgot_password`) |
| 14 | A reset link leaks: read from the database, sent on in a Referer header, or opened by a corporate mail scanner before the person clicks it. | Only the token's SHA-256 is stored. Links work once and expire in 30 minutes (60 for hand-delivered links). `/reset/*` is served with `Referrer-Policy: no-referrer`. Opening a link (`GET …/preview`) never consumes it; only submitting a new password does. | `api/app/auth/recovery.py`, `api/app/main.py` |
| 15 | An organizer uses a reset link to take over another organizer's or an admin's account. | Endpoint-level role matrix: organizers can reset participants and judges only; admins can also reset organizers; nobody can reset an admin or themselves from the UI. Admin recovery needs shell access to the host (`reset_link` CLI). | `api/app/auth/recovery.py` (`MAY_RESET`) |
| 16 | A dishonest organizer issues a reset link for a participant and uses it themselves. | **Accepted risk, mitigated rather than prevented:** every issue and redeem is in the audit log under the issuer's name; issuing is rate-limited to 30 per organizer per hour; the real owner is locked out by the change (so they notice immediately) and, with email on, is sent a "your password was changed" notice. | `api/app/auth/recovery.py`, `api/app/audit/` |
| 17 | A judge invited for one event is handed another event's submissions. | Assignment draws only from the event's `event_judges` panel. Judge invitations carry an `event_id`, and redeeming one enrols the judge on that panel only. | `api/app/judging/router.py`, `api/app/judging/invites.py` |
| 18 | One person enters the same hackathon twice through two teams. | `create_team`/`join_team` refuse a second team in the same event, and a unique index on `team_memberships(event_id, user_id)` stops two requests at once from both getting through. | `api/app/teams/router.py`, `api/app/db.py` |
| 19 | A judge scores a version of a project that its team later changes. | Assignment and scoring are refused until the event's `end_at`. After that, submissions are read-only. | `api/app/judging/router.py`, `api/app/scoring/router.py` |
| 20 | Password guessing, including one password tried across many accounts from one IP, or probing which emails are registered. | Only failed attempts count: 10 per account and 30 per IP per 15 minutes, checked *before* the password, so a correct guess made after the limit is still refused. Unknown emails run bcrypt against a dummy hash, so both answers take the same time, and the throttled response is identical either way. | `api/app/auth/router.py`, `api/app/ratelimit.py` |
| 21 | A submission link carries a script (`javascript:`, `data:`). | Links must be `http`/`https` with a host (checked server-side). They open with `rel="noopener noreferrer nofollow"` and are never embedded. | `api/app/submissions/schemas.py` |
| 22 | Winners leak before the results reveal. | `/winners`, gallery `awards` and submission `awards` are all withheld in the API response through `may_see_results`, the same gate as the standings. | `api/app/scoring/awards.py`, `api/app/submissions/router.py` |
| 23 | A draft event's existence leaks, or people join it early. | Drafts are left out of lists and the gallery, return 404 (not 403) to anyone but organizers, and refuse team creation. | `api/app/events/router.py`, `api/app/teams/router.py` |
| 24 | An admin account is used to lock out the other admins or create more admins. | The admin role can't be granted from the UI or API. Admin accounts can't be changed or deactivated from there, nor can an admin change themselves. New admins come only from the seed data or the server-side CLI. | `api/app/auth/admin_users.py` |
| 29 | **Clickjacking**: another site frames the judge console or a vote button under a decoy and tricks a signed-in user into clicking. | Every response sends `X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`, so browsers refuse to frame HackFlow anywhere. The only exception is the gallery widget at `/embed/events/{slug}`, which exists to be framed: it is read-only HTML with no script, no forms and no signed-in state, and it shows only what the public gallery shows to a stranger. | `api/app/main.py`, `api/app/embed.py` |

### The four attacks the DOGFOOD brief names

Each is stopped, partly stopped or not stopped.

| # | Attack | Status | What happens | Where |
|---|--------|--------|--------------|-------|
| 25 | **Sybil voting**: one person registers several accounts and votes from each. | **Mostly stopped, when the organizer turns it on.** | Two opt-in rules per event, both off by default so an offline install behaves as before. **Require a verified email**: an account votes only after following a signed link sent to its address (24 hours, tied to that address), so each extra account needs an inbox of its own; it can't be switched on while email is off, because nobody could verify. **Voter cutoff**: only accounts created before a time the organizer picks may vote, so accounts made to swing a result after the field is known are refused; this needs no email and works offline. Beyond the rules, votes from one client (IP + user agent) by several voters are listed for the organizer, who can void each one; the void writes the whole vote row to the audit log. `voting_access` still sets who votes at all: **signed-in accounts** (default), **anyone who confirms an email** (a signed 30-minute link; an address signed in and the same address as a guest share one voter key), or **anyone with the link** (a random id in a signed cookie, rate-limited per client). Every vote, withdrawal and void is audited. **Not stopped:** a person who controls several real inboxes and registered each account before the cutoff still gets several votes, and a person on several networks with several browsers isn't flagged. No CAPTCHA or device fingerprinting is built. The standard advice still applies: keep the community prize small and hide counts until the reveal (entry 5). | `api/app/voting/router.py`, `api/app/voting/voter.py`, `api/app/auth/router.py`, `api/app/audit/` |
| 26 | **Ballot stuffing**: one account votes many times, or a script floods the endpoint. | **Stopped.** | A unique constraint on (submission, voter) makes a second vote impossible at the database level, however many requests race. The rate limiter throttles the rest (entry 6). | `api/app/voting/` |
| 27 | **Judge collusion**: judges agree to push one project up or down. | **Not stopped.** | Normalization (`JUDGING.md`) removes each judge's *general* harshness or leniency, but a judge who is fair everywhere except one project keeps that bias. Conflict rules stop a judge scoring their own team's project, and declared conflicts are honoured (entries 3 and 17). Collusion between outsiders is not detected. What exists is evidence: raw per-judge scores are in the organizer's CSV export, and every score write is audited, so an organizer can review a suspicious outlier after the fact. | `api/app/scoring/normalization.py`, `api/app/judging/assignment.py` |
| 28 | **Deadline gaming**: submitting or editing after the close, or changing a project while it is being judged. | **Stopped.** | Every submission write checks the server clock against the event's `end_at` in the API, not in the browser, so a changed client clock or a crafted request is refused (400). Judging can't start until submissions close, so a scored version can't change afterwards (entry 19). | `api/app/submissions/router.py` (`_load_open_event`) |

## What this list does not cover

Denial-of-service, infrastructure-level attacks (the box itself, the network),
and social-engineering of an organizer's own account are out of scope for an
app-layer threat model like this one — see `ARCHITECTURE.md` for the
deployment boundary this app assumes it's running inside.
